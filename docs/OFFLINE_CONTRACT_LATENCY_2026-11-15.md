# Offline оценка сохранения решений и задержки

Цель: сократить повторную работу бота, сохранив все товары, оригиналы и свободу выбора источников. Ускорение всей консультации пока не доказано. Новый формат уменьшает выход, если модель сохраняет неизменённые основания. На точных сохранённых основаниях v11 выход увеличивается.

Этот этап содержит только анализ и локальный benchmark. Новых вызовов модели, web API и удалённого подсчёта токенов нет. PostgreSQL не запускался. Поведенческий код предыдущего пакета не изменён, публикации нет. Сообщение о независимом offline review предыдущего пакета принято как отдельный результат; этот анализ не является живой приёмкой.

## Что действительно известно о v11

Исследован ход `40febfbd-9f10-479a-abd4-2be2f73ef6a5`. От создания хода до сохранения ответа прошло **651,282 секунды**, с 20:54:31.542 до 21:05:22.824 UTC 14 ноября. Это серверный интервал. Времени доставки и отрисовки в виджете в экспорте нет.

Статус хода `recovered`, поле `recoveryAttempts` равно 0. Последняя запись web-этапа обновлена в 21:03:56.006 UTC, уже после отправки финального продолжения. Эти данные не позволяют восстановить число чтений, длительность пауз или утверждать отсутствие повторных POST в этом историческом ходе. Предыдущие локальные тесты проверяют запрет повторной отправки отдельно.

Два web-receipt занимают 6 061 и 5 136 байт, содержат по пять ссылок и 4 517 и 3 632 байта findings. Полных ответов web-провайдера нет.

## Как построено парное сравнение

Из 27 сохранённых JSON-артефактов собраны все 145 полных оригиналов той же версии каталога. Все 132 кандидата присутствуют, конфликтов original_card нет. Старые артефакты не изменялись. Карточки, история, вопрос и источники одинаковы у обеих сторон.

Старый конструктор запроса взят из `8882779`, новый из текущего локального пакета. Общие инструкции одинаковой версии, исходный префикс сохранённого агента извлечён из v11-инструкций. Следовательно, это контролируемое сравнение двух контрактов на сохранённых данных, а не точная копия исторического v11-request. Оригинальные request bodies и планы не экспортированы, их восстановление не заявляется.

Конструкторы работают с подставным транспортом. Удалённый endpoint подсчёта не вызывается; его mock возвращает 0 как служебное значение, не как оценку токенов. Общий `fetch` запрещён. Идентификаторы обёртки checkpoint тестовые, идентификаторы ответов в состоянии взяты из сохранённых данных. Заголовки авторизации, PostgreSQL JSONB, WAL, индексы и сетевой протокол не измеряются.

Выполнено пять чередующихся пар full/delta. Размеры во всех повторах одинаковы. Измеряется компактный JSON в байтах UTF-8, а не время модели, throughput или токены. Нагрузка Windows не влияет на детерминированный размер; время выполнения локального скрипта не используется как показатель ускорения.

Исходный response первой переоценки отсутствует. Поэтому запросы построены для нуля, одного и двух источников, но финальное сравнение выхода использует исходную оценку как базу сразу для двух источников. Недостающая промежуточная карта решений не выдумывается.

## Что уменьшилось и что выросло

После двух источников размеры запроса следующие:

| Компактный JSON | Полный контракт | Delta | Разница |
| --- | ---: | ---: | ---: |
| Весь request body | 1 517 955 | 1 558 129 | +40 174 |
| Input | 1 426 047 | 1 515 809 | +89 762 |
| Схема ответа | 57 276 | 7 672 | −49 604 |
| Сообщение с полными оригиналами | 1 397 107 | 1 397 107 | 0 |
| Сохранённый план в обёртке continuation checkpoint | 3 539 942 | 3 698 371 | +158 429 |

База оценок занимает 85 197 байт до вложения в строку input. Plan дополнительно содержит контекст и копию базы для восстановления. Эти вложенные размеры нельзя складывать друг с другом как независимый расход. Начальная оценка сохраняет прежнюю полную схему и все карточки, сокращения её работы не доказано.

Между сохранёнными начальной и финальной оценками изменились два решения, но **тексты оснований изменились у всех 132 товаров**. Проверены два разных сценария:

| Полный структурированный output, включая answer и source_review | Full | Delta |
| --- | ---: | ---: |
| Точные сохранённые финальные основания, 132 обновления | 39 992 | 42 075 |
| Условные два обновления, остальные 130 оснований оставлены начальными | 41 811 | 3 996 |

`source_review` отсутствует в историческом полном формате. Для таблицы использован явно помеченный offline placeholder объёмом 271 байт на два источника. Это не настоящая оценка применимости. Дополнительно проверен пример с копированием сохранённых findings: source_review занимает 8 476 байт, delta-output становится 50 280 и 12 201 байт соответственно. Эти два примера не являются нижней и верхней границами будущего ответа модели.

В условном случае двух обновлений request плюс output составляют 1 559 766 байт у full и 1 562 125 у delta с коротким placeholder. Общая сумма даже немного растёт. Из этого тоже нельзя сделать вывод о времени: вход, кэшированный вход, output и reasoning имеют разную стоимость обработки. Локальная оценка токенизации не выполнялась.

При точном сохранении финальных оснований новое состояние занимает 98 991 байт, отдельная контрольная точка состояния 99 102 байта. Результат `{answer, catalogReview}` занимает 105 605 байт против 6 597 у прежней обёртки `{answer}`. Это модель сериализации одной записи, не измерение суммарных записей или задержки PostgreSQL.

В обоих сценариях все 132 ID и основания совпадают с соответствующим парным full-output, все источники доступны, итоговый набор равен ожидаемым 34 ID. В точном сценарии основания также совпадают с реальным финальным response. Условный сценарий не доказывает, что модель сама сохранит 130 начальных оснований.

## Общий префикс и следующий шаг

Между реконструированными запросами после первого и второго источников общий префикс input превышает 1,41 МБ. Но полный сериализованный request совпадает только на первых 34 895 байтах у delta против 1 506 222 у full: раньше input меняется схема `source_review`. При реальной смене сохранённой базы изменяется ещё и enum `base_digest`.

Это наблюдение о JSON. Порядок сериализации токенов, ключи кэша и реальные cache hits провайдера неизвестны. Совпадение JSON-префикса не доказывает кэширование. На первом переходе меняются и инструкции, и формат полного ответа на delta.

В benchmark выполнена только проба в памяти: `base_digest` сделан строкой, а `source_review` массивом записей постоянной формы. Общий префикс request между двумя продолжениями вырос до 1 456 136 байт. Runtime-код не менялся, модель с этим форматом не тестировалась.

Следующий минимальный шаг: отдельно проверить стабильную схему продолжений, оставив ID источников и digest в данных, а проверку точного совпадения на сервере. Это не требует удаления оригиналов или ограничения решений агента. Локальный критерий: одинаковая схема между поисками, сохранность всех данных, отказ при чужом digest или ID, восстановление без лишнего POST. Проверяемый локальный выигрыш будет состоять в стабильности префикса, а выигрыш задержки останется гипотезой.

Для проверки реальной скорости затем нужны точные отметки отправки, завершения provider response, чтения, сохранения и доставки для каждого этапа, а также usage каждого response ID. После отдельного выпуска нужен сопоставимый диалог через настоящий виджет с аудитом всех 34 карточек и оснований. До этого нельзя обещать ускорение по разнице 39 022→330 байт из прежнего replay.

## Воспроизведение и проверки

Из корня проекта выполнить:

```powershell
python -X utf8 .agent/tasks/2026-11-15-contract-benchmark/analyze.py
npx tsx .agent/tasks/2026-11-15-contract-benchmark/benchmark.ts
python -X utf8 .agent/tasks/2026-11-15-contract-benchmark/verify.py
```

Результаты лежат рядом со скриптами: `source-inventory.json`, `timeline-and-usage.json`, `paired-results.json`, полные парные requests, outputs, checkpoints и `verification.json`. Отдельный проверяющий скрипт на Python заново проверил 47 условий, размеры JSON, ID и основания. Контрольные суммы 11 файлов предыдущего пакета и 27 исходных JSON не изменились. Это второй способ вычисления, не независимое ревью другим агентом.

Профильные тесты `catalogReviewState`, `platformAgentClient`, `controlledWebSearchAdapters`: **124 успешных теста**. Общая сборка заново не запускалась, поскольку runtime-код не менялся; прежние результаты 1977 тестов, typecheck и build относятся к предыдущему пакету. Повторные прогоны benchmark сначала выявили ошибку его подготовки истории и переход в полный формат. История исправлена, добавлена обязательная проверка `identity_updates_v1`; приведённые числа относятся только к последнему успешному прогону.
