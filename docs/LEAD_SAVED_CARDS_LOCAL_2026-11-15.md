# Названия и ссылки в новом письме из сохранённых карточек

Менеджеру удобнее получить название товара и прямую ссылку рядом с обязательным ID. Это локально подготовленное улучшение. Передача ID в опубликованном PR144 корректна и сохраняется.

Выбран простой источник, уже сохранённые `metadata.productCards` сообщения ассистента. Проверяются точный ID, доверенный platform runtime, UUID сообщения и совпадение `catalogRevision` с `knownProducts.source_revision`. ID должен присутствовать в knownProducts этого сообщения. Данные свободного ответа модели, пользовательская форма и новый каталог источниками названия и ссылки не являются.

Чат и форма используют один resolver. Он ограничивает историю первым появлением данной заявки включительно и выбирает последнюю достоверную карточку нужного ID до этой границы. Для прямой заявки без сохранённого offer доступна только уже сохранённая история. Изменения каталога или карточек после offer не подменяют исторический источник. Provenance сохраняется в outbox и новых snapshot metadata как `sourceMessageId` и `catalogRevision`.

Если карточка отсутствует, ID не совпадает, ревизия не подтверждена или источник неоднозначен, запись остаётся без обогащения с причиной. Совпадающее время разных source/request сообщений также считается неоднозначностью. Единственное сообщение самой заявки может содержать атомарно привязанную карточку. Общая сортировка истории и логика ответа агента не изменены. Никакой фильтрации пригодности товара нет.

Название сохраняется полностью, если укладывается в500 Unicode code points и не содержит управляющих символов. Более длинное или непригодное название не обрезается и не угадывается. URL допускается только точный публичный HTTPS `bakautprof.ru/catalog/`, без credentials, порта, query/hash, пробелов и управляющих символов. Недостоверное поле становится null, другое пригодное поле сохраняется. В письме рядом с ID явно написано «нет достоверного названия» или «нет достоверной ссылки», если соответствующего поля нет.

Структурные references проходят чат или серверную область формы, repository JSONB параметр$13, outbox decoder и новый email snapshot. Новых столбцов и миграций нет. Нормализация учитывает удаление null-ключей через PostgreSQL `jsonb_strip_nulls`. Resend по-прежнему получает только from/to/subject/text. Происхождение хранится в служебных metadata, а менеджер получает название, ссылку и ID.

Snapshot копирует данные до dispatch. Повторная отправка использует прежние body, idempotency key и references независимо от изменённого payload, истории и настроек. Старые snapshots и старые outbox без references не обогащаются задним числом. Согласие, проверка известных ID, session lock формы и durable outbox остаются прежними. Клиентские productReferences отвергаются строгой схемой формы.

Финальный полный прогон дал2122 прошедших теста, один PostgreSQL тест пропущен. Профильный прогон142/142 и независимый прогон142/142 прошли. Typecheck, build, no-regex и diff check прошли. Ревью PASS+NOTES привязано к11 текущим SHA-256. Отдельный offline replay ранее сохранённых production metadata собственной сессии подтвердил два исторических названия и ссылки без сетевого доступа. Тесты чата и формы проходят до fake HTTP письма; actual repository проверяется SQL mock. Реальная PostgreSQL семантика, доставка и отображение письма не подтверждены этим этапом.

Два прежних ZIP и три защищённых тестовых файла сохранили hashes. Снимки исходников до этапа, отдельный применимый в обратную сторону patch, результаты, review и повторяемый verifier находятся в `.agent/tasks/2026-11-15-lead-saved-cards/`. Команда повторной проверки `python .agent/tasks/2026-11-15-lead-saved-cards/verify.py`.

Платных API, сети для обогащения, реальных писем, PostgreSQL, установки и публикации в этом этапе не было. Код остаётся локальным поверх проверенного дерева PR144. Историческая карточка не является обещанием актуальности текущего каталога или наличия товара. Ближайшая граница перед отдельной публикацией, CI с PostgreSQL и проверка реального виджета по правилам проекта.
