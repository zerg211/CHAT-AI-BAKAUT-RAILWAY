# Заключение по товарному агенту

Цель: покупатель получает полезную предварительную оценку, полный подходящий список и самостоятельную проверку спорных фактов. База знаний остаётся основой; выбор следующего источника и вывод принадлежат модели.

## Что мешало

1. Политика ответа смешивала «не подтверждено буквально руководством» и «невозможно оценить». Из-за этого бот не давал покупателю предварительного решения.
2. Код ограничивал продолжение исследования: один пересмотр каталога, потеря источников при смене этапа, повторный старт поиска после web, общий таймер виджета.
3. Сохранённые запросы ошибочно не проходили проверку после перестановки ключей PostgreSQL JSONB. Отказ провайдера мог бесконечно восстанавливаться и удерживать диалог.
4. Ответы с простым перечнем ID смешивали товары и характеристики. Полный набор ID сам по себе не гарантировал правильного подбора.
5. Полные карточки читались повторно, переполняя контекст. В самой карточке также дублировались оригинал и его описания/характеристики.
6. Изменения приложения перезапускали каталог. Это обрывало обращения к нему во время поиска.

## Исправления и граница ответственности

Модель выбирает категории, источники, применимость фактов, пригодность оборудования, следующий поиск, уточнение или публикацию. В запросе явно сохраняются текущий этап, оригинальный вопрос, полные оригиналы и все результаты поиска. Прогноз отделён от гарантии и буквального подтверждения.

Код проверяет идентичность товара и версии каталога, структуру и покрытие решений, целостность сохранённого запроса, цены и порядок исполнения. Для каждого кандидата модель возвращает точное название, основание и решение. Это не заданный кодом фильтр по мощности или конкретной модели.

Проверен активный путь AssistantService → PlatformAgentAssistant. Старые ограничения AgentManagerOrchestrator в репозитории не являются ограничениями текущего runtime openai_platform_agent; их не удаляли вслепую. Следующее сопровождение должно опираться на реальный путь исполнения и отдельно изолировать старый код, чтобы он не создавал ложных выводов при ревью.

Последовательные поиски и пересмотры не имеют фиксированного числа шагов. Каждому шагу соответствуют сохранённый запрос и ключ отправки. HTTP-окна и повторное открытие виджета продолжают известный ответ; неизвестный исход отправки не запускает автоматический дубль. Явный отказ завершает ход и освобождает диалог. Готовое уточнение публикуется по решению модели, даже если исследование требует ответа покупателя.

Полные оригиналы передаются без удаления сведений. Массовое чтение известных карточек не повторяется инструментом того же запроса. Из контекста удаляются только точные копии полей, уже присутствующих внутри original_card; отличающиеся значения сохраняются. На сохранённом наборе 132 генераторов JSON уменьшился с 786622 до 494717 символов. Это измерение объёма, а не доказательство пропорционального ускорения.

Каталог запускается из GitHub-кода с проверенным снимком данных. Его watch path ограничен /catalog-service/**, поэтому изменения приложения не перезапускают каталог. Изменения публикуются только через GitHub main и автоматическую сборку Railway.

## Проверка результата

Протокол всех живых попыток, включая провалы: [PRODUCTION_RESEARCH_2026-11-14.md](PRODUCTION_RESEARCH_2026-11-14.md). Проверка выполняется через настоящий виджет bakautprof.ru с сохранением истории. Успешные unit-тесты и CI не заменяют её.

Подтверждён полезный первый ответ о щебне 20–40 слоем 30 см: предварительный выбор DPU 6555, объяснение по характеристикам и внешнему ориентиру, отделение прогноза от гарантии. Ответ ещё избыточно осторожен и длинен. На v11 полный подбор генераторов прошёл проверку: 34 из 34 ожидаемых товаров, без лишних позиций; названия и цены совпали с каталогом. Агент сам выполнил два поиска по спорным артикулам и использовал оба результата. Виджет раскрыл 10→20→30→34 карточки.

В продолжении на v11 отдельного вывода по второй плите всё ещё не хватало. После исправления общей политики на v12 и ответа покупателя на уточнения бот отдельно оценил обе модели как вероятно подходящие, обосновал предпочтение DPU 6555 и сохранил исходный режим одного рыхлого слоя. Ответ занял около 44 секунд. Он не выдал прогноз за гарантию проектной плотности. Это проверено в сохранённой истории, а не в отдельном новом диалоге без контекста.

Главный оставшийся недостаток: полный подбор занял 10 минут 51 секунду. Корректность подтверждена для описанных сценариев; скорость и краткость требуют дальнейшего улучшения. Общая проверка всех вопросов и всех карточек каталога не проводилась. Функциональные критерии выпуска выполнены, но это не заявление об универсальной безошибочности бота.

Опубликованные изменения поведения: PR130, PR132–137, PR139–141. Текущая проверенная версия поведения: 4560825df46338f74b9f24eed100446d9ac3d585, marker v12. Обязательные проверки типов, сборки, тестов и PostgreSQL прошли; последний полный набор содержит 1962 успешных теста и один пропущенный. Число испытаний не ограничено искусственной квотой. Технические ограничения провайдера, отмена пользователем и действующий учёт расходов сохраняются.

## Следующие шаги и критерии

| Шаг | Что сделать | Как проверить |
| --- | --- | --- |
| 1 | Зафиксировать набор реальных диалогов по пригодности, сравнению, смене условий, конфликту источников, неизвестным данным и полному подбору | Для каждого проверять первый ответ, каждый товар, полный список, ссылки и внутреннюю трассу. Число испытаний не ограничивать искусственной квотой |
| 2 | Сохранять найденные факты с точным исполнением, ссылкой, датой и областью применимости | Данные соседнего артикула не становятся характеристиками выбранного; общий инженерный ориентир остаётся обозначенной оценкой |
| 3 | Сохранять решения по ID и ссылки на основания после каждого этапа; при новом источнике давать агенту пересматривать нужные решения без обязательной повторной выдачи всей классификации | Повторить тот же набор 132 кандидатов: итоговые 34 ID, цены и основания сохранены; все изменения решений имеют источник; измерить время и токены до/после. Агент может пересмотреть любой товар, код не выбирает пригодность |
| 4 | Добавить независимое фоновое исполнение, если ответ должен завершаться при закрытой вкладке | Закрыть виджет, перезапустить приложение, открыть снова: один итоговый ответ и отсутствие повторных POST по уже созданным шагам |
| 5 | Отдельно улучшать базу знаний | Проверять единицы, модификации, конфликтующие характеристики и применимость документов. Не исключать товар только из-за пробела; исследовать спорный факт |
| 6 | Закрепить настройки инфраструктуры в поддерживаемой конфигурации | Проверять SHA приложения, хеш кода каталога и неизменность снимка данных после публикации |

Оставшиеся границы: контекст и доступность провайдера конечны; длинный полный подбор может занимать минуты. Работа без активного виджета пока не обещается. Исправления поведения не означают полной проверки качества всех 4324 исходных карточек.

Для категорий, не помещающихся в одно окно модели, следующий архитектурный шаг: поэтапное чтение полных оригиналов с сохранением всех кандидатов и решений между окнами. Проверять полноту по множеству ID, перенос источников, возможность изменить прежний вывод и отсутствие повторной оплаты уже выполненного шага. Нельзя решать переполнение сокращением подходящего списка или скрытым числовым фильтром в коде.
