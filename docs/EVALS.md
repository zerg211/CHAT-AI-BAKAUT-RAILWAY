# Evals

## Цель

Проверять не только “ответил ли бот”, а ведет ли он себя как менеджер: понимает контекст, не галлюцинирует, использует скрытые потребности, подбирает товары и соблюдает бизнес-ограничения.

## Обязательные сценарии

- Неопределенная потребность: “Нужно что-то для участка”.
- Скрытый критерий: “Жена будет сама переносить”.
- Смена требований: сначала нужен генератор для дома, затем покупатель уточняет, что нужен для бригады.
- Подбор виброплиты под грунт/плитку/асфальт.
- Подбор генератора под нагрузку.
- Вопрос по эксплуатации и обслуживанию.
- Запрос скидки.
- Запрос наличия.
- Запрос доставки.
- Конфликт характеристик товара.
- Нет данных в каталоге, нужен web search.
- Два одинаковых коротких сообщения как разные действия и retry одного `clientMessageId`.
- Прерывание после tool/lead/response preparation и точное восстановление без дубликатов.
- Диалог длиннее 80 событий: исправление, смена темы и возврат к приостановленной задаче.
- Неизвестный класс оборудования, который нельзя насильно свести к старой taxonomy.
- Число в разных ролях: бюджет, мощность нагрузки, требуемая мощность товара, вес и количество.
- Строгий запрет на альтернативу и разрешённый компромисс с объяснением.
- Отказ дать контакт без повторного давления и успешный lead capture после явного согласия.

## Критерии прохождения

- Нет выдуманных характеристик.
- Нет обещаний по скидкам, наличию и точной доставке.
- Ассистент учитывает скрытые потребности, но не выдает их как подтвержденный факт без основания.
- При неполной потребности задает короткие полезные уточнения.
- При готовом подборе показывает 2-4 варианта и объясняет выбор.
- Новые данные не смешиваются со старыми.
- Planner contract содержит семантическое действие, роли/строгость requirements и alternative policy; код не переопределяет их по ключевым словам.
- Все названные товары и фактические claims имеют актуальный catalog/web/tool evidence.
- Карточки совпадают с текстом, выбранными IDs и hard constraints; unknown fact не проходит как fit.
- Retry/recovery возвращает тот же payload и не повторяет side effects.

## Локальный release gate

```bash
npm run verify
```

Gate проверяет Node.js `>=22`, запрет нового semantic regex debt без изменения baseline, production dependency audit, typecheck, полный unit/integration suite, agentic eval и build. CI выполняет тот же gate на Node.js 22; локально допустима более новая поддерживаемая версия. Локальные OpenAI-вызовы в этой среде не используются как сигнал качества.

`npm run feedback:export-evals -- --output .private/feedback-candidates.json --acknowledge-unverified-residual-pii` создаёт PII-reduced candidate fixtures из негативной очереди. Редакция персональных данных best-effort: флаг является явным подтверждением остаточного риска, файл нужно держать приватным и вручную проверить на имена, адреса и social handles. Candidate не становится эталоном автоматически и не должен попадать в git до этой проверки.

## Production gate

После commit/push нужно дождаться соответствующего marker в Railway `/api/health`, затем провести адаптивный диалог только через встроенный виджет `https://bakautprof.ru/`. Следующая реплика формируется после чтения фактического ответа. Каждый turn проверяется с двух сторон: покупательский UI/карточки и admin trace/metadata/checkpoints/tool evidence. Автоматический `PASS` без этого аудита недостаточен.
