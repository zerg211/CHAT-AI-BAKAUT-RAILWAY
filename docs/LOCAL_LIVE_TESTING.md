# Production Widget Live Testing

## Когда обязательно

Любое изменение, влияющее на поведение AI-ассистента в проде:

- промпты;
- извлечение потребностей;
- retrieval;
- web search routing;
- guardrails;
- карточки рекомендаций;
- обработка заявок в диалоге.

Проверка запускается только после успешного `npm run verify`, commit/push и подтверждения нового commit/runtime marker в production `/api/health`. Локально разрешены typecheck, unit/integration tests с моками, build и статический аудит; локальный OpenAI/Promptfoo live harness в этой среде получает региональный 403 и не является доказательством поведения.

## Как проводить

Проверка через `localhost`, локальный iframe или прямой API запрещена как доказательство готовности продового поведения. Валидная live-проверка проводится только через встроенный виджет чата на `https://bakautprof.ru/`.

1. Открыть `https://bakautprof.ru/`.
2. Открыть встроенный виджет чата на сайте.
3. Провести живой диалог в интерфейсе виджета.
4. Перед каждой следующей репликой покупателя прочитать фактический ответ ассистента в интерфейсе.
5. Тема проверки может быть задана заранее, но реплики покупателя не должны быть заранее написанным жестким сценарием.
6. Следующий ход покупателя формируется только из фактического ответа ассистента: его уточнения, показанных карточек, аргументов, ошибок, недосказанности или следующего естественного вопроса покупателя.
7. Если ассистент задал уточнение, отвечать на него; если показал неподходящие карточки, возражать по ним; если дал неполный ответ, просить уточнить именно пропущенную часть.
8. Не считать валидной live-проверкой прогон, где сессия была сброшена, история текущего диалога не прочитана или реплики покупателя отправлялись как случайные заготовки без связи с ответами ассистента.
9. Оценить каждый ход глазами покупателя: правильно ли ассистент ответил на заданный вопрос, не спрятал ли нужную карточку, не показал ли неподходящий товар, не противоречит ли текст карточкам, не задал ли лишний вопрос и не ушел ли от прямого ответа.
10. Оценить каждый ход технически: проверить историю в БД или admin endpoint, `turnContract`, `productCards`, `structuredCatalogSlice`, warnings, recovery/fallback, логи и соответствующие участки кода, которые привели к такому поведению.
11. Не считать `PASS` автоматического сценария достаточным результатом. `PASS` означает только прохождение узких проверок скрипта; итоговый verdict ставится только после аудита видимого ответа покупателю и аудита внутренней работы по metadata/логу/коду.
12. Сохранить протокол.

Минимальное release-покрытие включает: повтор одинаковых коротких ответов, recovery; correction/topic switch/return после длинной истории; технический вопрос с web evidence; catalog comparison; изменение hard constraints; отказ от контакта; успешную заявку; вопрос о наличии/доставке без неподтверждённых обещаний.

## Правило живого диалога

Live-тест проверяет не отдельные промптовые фразы, а поведение ассистента в реальном разговоре. Поэтому допустимо заранее выбрать тему, например "подбор генератора в кожухе 5-6 кВт", но нельзя заранее зафиксировать все реплики покупателя. После каждого ответа бота тестировщик обязан прочитать видимый ответ и только потом написать следующий естественный ход покупателя.

## Шаблон протокола

Файлы протоколов хранятся в `local-live-tests/*.production.md` или другом `.md` файле с явным указанием, что проверка была проведена через виджет на `bakautprof.ru`; они не коммитятся.

- Каждый ход проверен по metadata/логу/коду:
