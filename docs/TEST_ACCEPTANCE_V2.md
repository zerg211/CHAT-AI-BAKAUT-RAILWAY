# БАКАУТ — готовая замена приёмочных тестов, v2

**Проект:** `zerg211/CHAT-AI-BAKAUT-RAILWAY`.
**Базовый коммит:** `3b47e6a91f728a27e29be1e84cd1d5c8c2b28ef6`.
**Дата комплекта:** 7 сентября 2026 года.

В архиве находятся исполняемые тесты, независимые оценщики, новый HTTP/SSE-клиент, изолированный хост настоящего приложения, тестовые данные, калибровка LLM-оценщика, проверки искусственно повреждённых оценщиков и установщик. `payload/` — готовые файлы для репозитория. Это не прежний список из 38 пожеланий: сценарии исполняются `runner.cjs`.

## 1. Граница результата

Подтверждены локальные проверки кода нового оценщика, HTTP-клиента и защит запуска; точные результаты находятся в `verification/VERIFICATION.json`. Реальные вызовы OpenAI, запуск PostgreSQL/приложения, полный существующий `npm run verify` и браузерная проверка production здесь НЕ выполнялись. Новые тесты не дают им зелёный статус задним числом.

Пакет проверяет правильность собственного решения «принять/отклонить» на позитивных и негативных примерах. Отдельно он содержит исполняемую приёмку настоящего агента. Проверенность тестового механизма и прохождение экзамена самим агентом — разные результаты. Ни конечный набор примеров, ни LLM-оценщик не гарантируют отсутствие всех будущих ошибок.

## 2. Установка в локальную копию проекта

Нужны Node.js 22+, Git и чистая отслеживаемая рабочая копия указанного коммита. На другой версии установщик остановится вместо автоматической перезаписи чужих изменений. Windows CRLF учитывается.

Из папки распакованного архива:

```powershell
node APPLY.cjs --check "C:\projects\CHAT-AI-BAKAUT-RAILWAY"
node APPLY.cjs --apply "C:\projects\CHAT-AI-BAKAUT-RAILWAY"
```

Для Linux используется тот же синтаксис с путём вида `/home/user/project`.

Установщик проверяет Git blob-хеши изменяемых старых файлов; создаёт резервную копию в `.private/acceptance-backup-*`; применяет изменения только к тестам, оценщикам, npm-командам и названию CI; запускает новые бесплатные проверки. При ошибке записи пытается откатить записанные изменения. Повторная установка поверх изменённых файлов намеренно запрещена.

**Не изменяет `src/`, зависимости, переменные Railway, ключи и бизнес-логику. Не выполняет commit, push, merge, deploy или платные вызовы.** После установки штатный `npm run verify` остаётся отдельной проверкой интеграции с остальным репозиторием. Успех новых локальных тестов не подменяет её результат.

## 3. Что исправлено и что исключено

| Старая проверка | Замена |
|---|---|
| План вызова инструмента засчитывался как его исполнение | Только артефакты исполнения данного хода; отдельно attempted / succeeded / verified fact |
| Ошибка web считалась успехом поиска | Ошибка, успешное чтение, подтверждённый факт и попадание в память различаются |
| Старые карточки/класс скрывали дефект нового ответа | Ожидания проверяются на каждом конкретном ходе |
| Агент сам объявлял «данных нет» и получал освобождение от проверок | Независимый каталог, ограничения покупателя и разрешённые исходы; общего освобождения нет |
| Длина ответа и ключевые слова служили качеством | Удалены из приёмки; короткий правильный ответ и предварительный подбор разрешены |
| Оговорка о скидке скрывала обещание доставки | Раздельная смысловая оценка обязательств, с негативным примером этого обхода |
| Зелёная самопроверка агента считалась независимым доказательством | Приватный trace нужен для фактов исполнения, но его оценка «pass» не является эталоном качества |
| Тестовый клиент ждал закрытую metadata в публичном SSE | Чтение admin API, строгая привязка к turnId и assistantMessageId |
| Timeout прекращался при получении HTTP-заголовков | Deadline действует до конца тела/SSE |
| Повторы скрывали первоначальные неудачи | Все попытки остаются в отчёте; нельзя выбрать один удачный повтор |
| Фиксированный обязательный запрет на восстановление/осторожность | Проверка полезного результата, соответствия фактам и идемпотентности |
| Четыре Vitest-файла запускались повторно как «agentic eval» | Повторный этап удалён из release gate; реальные модельные тесты запускаются отдельно |
| Файл сценариев тестировался по количеству строк/реплик | Удалён старый тест; новый компилятор проверяет выполнимость требований и неизвестные параметры |

Удаляются из активного Vitest-набора **ровно два проверенных файла**: `tests/promptfooAssertions.test.ts` и `tests/salesManagerSelectionScenarios.test.ts`. Их новая проверяемая логика находится в `tests/acceptance/legacy.test.cjs`, `engine.test.cjs` и `suite.test.cjs`. Оригиналы сохраняются в локальной резервной копии. Остальные unit-, security-, recovery-, database- и UI-тесты не удаляются вслепую.

`evals/promptfoo/assertions.cjs` заменяется совместимыми именами функций, делегирующими независимому оценщику. Для смысловой оценки нужны независимые данные и отдельный вердикт, а не только старые keyword-настройки. Старый `promptfooconfig.yaml` больше не запускает слабую платную цепочку: он явно возвращает ошибку о её замене. Прежний production exploratory-скрипт остаётся в истории/дереве как диагностический материал, но его npm-команда не является приёмкой.

Название GitHub CI меняется на **Code and Oracle Checks**. Зелёный CI означает только соответствующие локальные проверки. Настройки защиты ветки и автоматического деплоя GitHub/Railway этим архивом не меняются.

## 5. Безопасный стенд настоящего приложения

Нужна **отдельная пустая PostgreSQL/pgvector-база** с именем `bakaut_acceptance_*` на loopback. Используется существующий драйвер `pg` и существующие миграции проекта. Хост отказывается работать с произвольной или непустой товарной базой.

Пример переменных PowerShell; пароль, путь и API ID задаются для вашего тестового окружения:

```powershell
$env:DATABASE_URL = "postgres://postgres:TEST_PASSWORD@127.0.0.1:5432/bakaut_acceptance_local"
$env:BAKAUT_EVAL_ISOLATED_DB = "YES"
$env:OPENAI_API_KEY = "YOUR_TEST_AGENT_API_KEY"
$env:BAKAUT_EVAL_AGENT_MODEL = "YOUR_ACTUAL_AGENT_MODEL_ID"
$env:BAKAUT_EVAL_JUDGE_API_KEY = "YOUR_APPROVED_JUDGE_API_KEY"
$env:BAKAUT_EVAL_JUDGE_MODEL = "YOUR_JUDGE_MODEL_ID"
npm run migrate
npm run build
npm run test:acceptance:host
```

Не используйте рабочую базу и не копируйте её персональные данные. Миграцию запускайте только после явной проверки `DATABASE_URL`. Хост дополнительно проверит адрес и имя БД, наличие исключительно тестовых товаров и получит advisory lock. Ключи не записываются в исходники. Не добавляйте `.private/` в Git.

Хост импортирует **настоящий `buildApp()`**, настоящие репозитории, оркестратор и OpenAI-код. Планировщик, writer и reviewer не подменяются заготовленными правильными решениями. В `NODE_ENV=test` штатный email-worker не запускается; email-настройки очищены. Сам старт хоста не вызывает модель. Конфигурация ролей задаётся явно, а не скрыто переключается тестами.

`NODE_ENV=test` и синтетический каталог — намеренная изоляция. Это не доказательство полной идентичности production-сетей и конфигурации. Стенд записывает commit, хеш `src/` и настроенные модели. Проверка реального production-виджета остаётся отдельным этапом, для неё архив не фабрикует выполненный результат.

Тестовые товары `BAKAUT-TEST` и их характеристики вымышлены. Они позволяют знать правильный ответ заранее. **Их нельзя выгружать в рабочий каталог или показывать покупателям.** Сценарий A39 дополнительно проверяет настоящий внешний источник; A40 проверяет честный исход независимого поиска для синтетической модели, для которой нельзя выдумывать официальный документ.

## 6. Порядок без бессмысленного расходования лимитов

Сначала локальные проверки и mutation-проверка. Затем `test:acceptance:backend`: этот этап проверяет доступ к истории с чужим visitorId, защиту admin API, доступность сохранённого технического факта и сохранение этой доступности при изменении только цены. **Он не отправляет сообщения модели.**

В live-команду эти бесплатные backend-проверки также включены до калибровки и диалогов. Если обнаружен дефект приложения, дорогое тестирование не начинается. Проверка `PRICE_CHANGE_PRESERVES_TECHNICAL_MEMORY` специально не ослаблена под прежнюю реализацию.

Первый ограниченный запуск во втором терминале:

```powershell
npm run test:acceptance:list -- --ids A01,A05
npm run test:acceptance:live -- --ids A01,A05 --approve-paid --max-agent-turns 2 --max-judge-calls 3 --max-http-requests 100
```

Полный план сначала выводится командой `test:acceptance:list`. Укажите бюджеты не ниже выведенного плана. Список сценариев нельзя незаметно сократить и получить общий допуск: недостающие обязательные ID будут перечислены как неподтверждённые. `--repeat 3` сохраняет все три попытки; неудачная первая не исчезает из результата.

Ограничены число отправок сообщений в агент, число вызовов оценщика и общее число HTTP-запросов. Восстановительный повтор сохраняет `clientMessageId`. **Количество HTTP-ходов не равно количеству внутренних OpenAI-вызовов и не является жёстким долларовым лимитом.** Внутренние модельные стадии ограничиваются приложением. Клиентская отмена не обещает остановить уже начавшуюся обработку на сервере. Используйте согласованные ключи/бюджеты тестового окружения; фактическое использование оценщика сохраняется в отчёте.

Оценщик использует Responses API напрямую, с JSON Schema, без автоматических повторов и без молчаливого обрезания важных доказательств. Сведения о мире дедуплицируются. Перед диалогами одной отдельной оценкой проверяются 16 эталонных примеров: восемь хороших и восемь плохих. Это прозрачная синтетическая калибровка; она не выдаётся за экспертную разметку реальных покупателей. При её провале прогон останавливается.

## 7. Смысл вердиктов

- `PASS`: все проверки данного теста выполнены и пройдены.
- `FAIL`: обнаружено нарушение поведения/числового ограничения/состояния.
- `INCONCLUSIVE`: доказательств недостаточно, оценщик/сборщик сломан, источник недоступен или данные не согласованы. Это не успех.
- `NOT_RUN`: соответствующая проверка не исполнялась.
- `READY_FOR_THIS_SUITE`: полный актуальный набор реальных сценариев прошёл для данного кода/данных после backend-проверок и калибровки. Это не обещание отсутствия всех будущих ошибок.

Критическое нарушение не усредняется красивым стилем. Одна чужая модификация, неподтверждённая цена как достоверная, потерянное обязательное требование или неверная заявка блокируют сценарий. Реальная доступность источника и полезность ответа при сбое проверяются раздельно. Источник, который не удалось прочитать, не превращается в подтверждение факта.

Временные пороги заданы явно в сценариях: обычно 12 секунд до полезного содержания для точного вопроса, 20 секунд для каталожного подбора и 45 секунд для внешнего исследования. Это **проектные пороги приёмки**, не измеренные показатели текущего бота и не универсальные нормативы. Индикатор «проверяю» за полезное содержание не считается. Изменение порогов меняет хеш набора; старый отчёт перестаёт подтверждать новый набор.

## 8. Где читать ошибки

Приватный JSON-отчёт содержит каждый диалог и ход, исходную реплику, текст и карточки, артефакты исполнения, независимую оценку по критериям, длительность и все попытки. Повторяющиеся ошибки имеют стабильные коды: `CARD_CONSTRAINT`, `WRONG_MODIFICATION`, `MISSING_CURRENT_CARDS`, `TOOL_OBLIGATION`, `MEMORY_REQUIREMENT`, `FACT_MEMORY_MISSING`, `OUTBOX_STATE`, `LATENCY_USEFUL` и другие.

Ошибка данных теста имеет отдельный префикс `HARNESS_*` или `JUDGE_*`. Нельзя «чинить» приложение ради удовлетворения некорректного ожидания теста. Нельзя, наоборот, стирать проверку ради зелёного результата. Для каждого найденного дефекта используйте позитивный контроль и соседние случаи уже существующего семейства.

## Интеграция в этот репозиторий, 7 сентября 2026

Комплект установлен из пользовательского `BAKAUT_TESTS_V2`: исходные 23 payload-файла проверены по SHA256 перед применением. Последующие изменения интеграции:

- Mutation runner явно запрашивает TAP у Node, чтобы действительно посчитать упавшие проверки, независимо от стандартного reporter установленной версии Node.
- Общий fingerprint учитывает `src`, `sql`, `package.json`, `package-lock.json`; hash сценариев включает сам механизм fingerprint. Проверяются текущий commit и загруженный код хоста. Изменённый файл на диске не выдаётся за обновившийся работающий сервер: нужен его перезапуск.
- GitHub Actions выполняет бесплатные oracle/mutation-проверки, миграции и реальные DB/backend-контракты в отдельной PostgreSQL. `network-guard.cjs` блокирует внешний HTTP; фиктивный ключ в этом шаге не даёт доступа к OpenAI.
- `node --import tsx tests/knowledgeDatabase.integration.mjs` проверяет технические версии, сохранение памяти и embedding при смене цены, выборку нужного атрибута, дедупликацию, lease/retry, порядок дат источника и смену модификации. Требуется явно заданная локальная база `bakaut_acceptance_*`.
- Локальный полный прогон модели в данной среде запрещён проектным AGENTS.md из-за регионального 403. `OFFLINE_ORACLE_PASS` и реальные проверки БД не означают `READY_FOR_THIS_SUITE`. Незапущенные 45 сценариев живой модели остаются `NOT_RUN`.
- Production-поведение проверяется отдельно адаптивным диалогом через встроенный виджет на `bakautprof.ru`, с разбором каждого ответа и внутренних traces. Синтетические товары `.invalid` на production не загружаются. Каталоги `.private` и `evals` исключены из Docker build context.
