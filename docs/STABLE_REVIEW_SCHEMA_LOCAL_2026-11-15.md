# Стабильная схема продолжений, локальный этап

Бот должен сохранять все товары и основания, самостоятельно выбирать источники и пересматривать любой вывод. В этом этапе форма схемы продолжения больше не меняется из-за нового digest или состава источников. Проверка точных значений осталась на сервере.

Изменения сохранены локально в ветке `perf/catalog-review-state-local-20261115`, поверх предыдущего локального пакета. Платные API и удалённый token counting не вызывались. PostgreSQL не запускался. Push, PR, публикации и изменений каталога нет.

## Изменение и совместимость

Новые планы используют `identity_updates_v2`. Поле `base_digest` имеет тип string, его точное значение передаётся в сохранённом состоянии. `source_review` теперь массив записей `{response_id, assessment}` постоянной формы. Enum кандидатов продолжает включать весь допустимый набор. Схема стабильна внутри исследования одного набора, а не между произвольными наборами каталога.

Сервер требует точного digest, ровно одной непустой оценки каждого доступного источника и отсутствия посторонних источников. Он отклоняет повторные и чужие ID товаров, ошибочное точное название, пустое основание и отсутствующий массив изменений. Неполная или повреждённая исходная карта решений не переносится. Пустой массив изменений допустим, поскольку полная карта сохраняется в состоянии. Модель может обновить любое число товаров, включая все, и изменить любое основание.

Ранее сохранённые планы `identity_updates_v1` читаются по прежнему формату с объектом source_review. Версия берётся из manifest, защищённого контрольной суммой плана. Формат ответа не угадывается по JSON. Ответ v2 для сохранённого плана v1 отклоняется. Неизвестная или отсутствующая версия при наличии базы, а также update-план без базы отклоняются до транспорта.

Внутреннее состояние остаётся `version:1`, source_review хранится в прежней карте. Миграция состояния не требуется. После чтения старого результата следующий новый план использует v2. Совместимость проверена на fixture плана, созданного замороженным локальным конструктором v1 до изменения схемы. Это не утверждение о миграции уже развёрнутой production-версии.

## Парное сравнение полного, v1 и v2 контрактов

Использованы те же 145 полных оригиналов, 132 кандидата, история и два источника из предыдущего benchmark. Старые 32 файла не изменены, SHA-256 сверены. Конструктор v1 заморожен отдельно. Его размеры совпали с прежними результатами, исходный full-контракт тоже воспроизведён.

Пять чередующихся повторов дали одинаковые размеры. Ниже приведены байты UTF-8 компактного JSON после двух источников:

| Объект | Исходный full | Delta v1 | Delta v2 |
| --- | ---: | ---: | ---: |
| Весь request body | 1 517 955 | 1 558 129 | 1 558 139 |
| Input | 1 426 047 | 1 515 809 | 1 515 809 |
| Схема ответа | 57 276 | 7 672 | 7 682 |
| Сообщение со всеми оригиналами | 1 397 107 | 1 397 107 | 1 397 107 |
| План в обёртке continuation checkpoint | 3 539 942 | 3 698 371 | 3 698 381 |
| Полный output с точными финальными основаниями, 132 обновления | 39 992 | 42 075 | 42 133 |
| Полный output в условном сценарии двух обновлений | 41 811 | 3 996 | 4 054 |

Выход включает answer и source_review. Оценки применимости источников в таблице заменены явно помеченным offline placeholder. Реального source_review модели в сохранённых ответах нет. Дополнительный пример с копированием полных findings также проверен: для 132 обновлений output v2 составляет 50 338 байт, для двух обновлений 12 259. Это примеры размера, не границы будущего ответа модели.

Во всех парных вариантах сохранены все 132 ID, точные названия и основания; итог равен прежним 34 ID. В точном сценарии совпадают все 132 основания реального финального response. В условном сценарии сохраняются 130 начальных оснований и меняются два, поэтому он не заменяет точную проверку. Состояния после декодирования v1 и v2 полностью равны. Например, точное финальное состояние с коротким placeholder занимает 98 991 байт, его отдельный checkpoint 99 102 байта у обеих версий.

Само это изменение практически не сокращает объём: при двух источниках request вырос на 10 байт, output на 58. Его проверяемый результат состоит в постоянной схеме:

| Между продолжениями после первого и второго источников | Full | V1 | V2 |
| --- | ---: | ---: | ---: |
| Общий префикс сериализованного request, байты | 1 506 222 | 34 895 | 1 456 645 |
| Схема полностью одинакова | Да | Нет | Да |

Дополнительная проверка изменила сам digest базы и все финальные основания. Схема v2 осталась прежней, общий префикс request составил 1 491 160 байт. Input и инструкции не урезались. После первой полной оценки формат всё ещё переключается с полной карты на обновления; стабильность этого перехода не заявляется.

Это не измерение токенов, cache hits или скорости. Сериализация и кэш провайдера могут отличаться от JSON. Сохраняются прежние расходы на полный вход, состояние, начальную оценку и выбор источников. Точные исторические requests и полный промежуточный response не экспортированы, поэтому финальный benchmark по-прежнему сравнивает исходную карту с итогом после двух источников, без выдумывания промежуточных оснований.

## Воспроизведение и граница следующего этапа

Локальные артефакты находятся в `.agent/tasks/2026-11-15-stable-review-schema/`. Полные requests, outputs и checkpoints сохранены для каждой стороны. `benchmark-results.json` содержит размеры и префиксы, `verification.json` фиксирует проверку данных и неизменности старых файлов.

```powershell
npx tsx .agent/tasks/2026-11-15-stable-review-schema/benchmark.ts
python -X utf8 .agent/tasks/2026-11-15-stable-review-schema/verify.py
```

Для старого контракта новый benchmark использует замороженный код, а не текущую реализацию. Прежний benchmark и его отчёт не переписывались. Его старый скрипт, импортирующий текущий runtime, нельзя считать неизменным v1-экспериментом после обновления runtime.

Перед выпуском нужны независимое ревью этого изменения и проверка контрольных точек на PostgreSQL. Затем при отдельном выпуске требуется живой диалог через виджет `bakautprof.ru`: новый поиск, пересмотр прежних решений, отсутствие изменений и раскрытие всего списка по 10. Нужно проверить каждый ответ и основание вместе с метаданными.

Главные оставшиеся риски: модель может ошибиться в новой форме source_review, пропустить нужный пересмотр или дать слабое основание. Сервер отклонит неправильный формат, но структурная валидность не доказывает качество консультации. Выигрыш кэша и задержки требуется измерить по фактическим usage и отметкам каждого этапа после отдельной публикации. Готовность к production и ускорение в этом локальном отчёте не заявляются.
