## Objective

Implement an agent-manager harness for the BAKAUT site chat so the bot behaves like an AI sales/support manager:

- LLM owns semantic understanding, dialogue strategy, tool-result evaluation, comparison logic, and final wording.
- Code owns durable state, typed tool execution, calculations, schema validation, policy enforcement, idempotency, checkpoints, and persistence.
- User-visible answers must not be generated by deterministic technical templates, regex routes, or append-only state artifacts.
- If a buyer message is saved, answer generation failures recover the same turn from checkpoints instead of asking the buyer to repeat the question or showing a generic error.

## Non-goals

- Do not build a scenario/keyword bot.
- Do not let code decide buyer intent with regex and then render final text.
- Do not create a global memory of buyer-specific dialogue context across sessions.
- Do not promise final delivery, stock, discounts, dates, or special commercial terms without specialist/logistics verification.
- Do not implement manual Railway deploy as part of this plan.

## Target Architecture

```text
Saved user message
-> AgentOrchestrator
-> ResumableTurnExecutor
-> LLM reads current dialogue context and DialogueLedger
-> LLM proposes LedgerStateDelta
-> DialogueLedgerReducer applies typed events idempotently
-> LLM decides what answer/work is needed without fixed scenario menu
-> LLM requests typed tools when needed
-> code executes tools mechanically and stores checkpoints/tool artifacts
-> LLM evaluates tool results
-> LLM returns AnswerContract with answerText
-> PreSendAnswerReviewer checks risky answers/questions/claims
-> assistant message is saved idempotently in the same turn
-> widget receives saved final answer or reconnects to it
```

## Prompt Contracts

Prompts must ask for structured outputs, not hidden scenario choices.

### `DialogueStateExtractor`

Input:

- current session dialogue summary;
- latest user message;
- current ledger snapshot;
- visible cards and selected products;
- business rules.

Output:

- `LedgerStateDelta`.

Rules:

- Do not copy context from other sessions.
- Mark corrections as `fact_negated` or `fact_superseded`.
- Close questions through `question_answered` events.
- Every event requires evidence from the current session or tool result.

### `IntentPlanner`

Input:

- ledger snapshot;
- latest user message;
- tool availability;
- budget tier limits.

Output:

- `AgentIntentContract`.

Rules:

- Do not choose from a fixed scenario menu.
- Use `nextWork.kind='other'` with rationale for unusual cases.
- Ask only questions that have `asksForSlot` and `whyNeeded`.

### `AnswerWriter`

Input:

- ledger snapshot;
- intent contract;
- tool artifacts;
- business rules;
- card manifest;
- source facts.

Output:

- `AnswerContract`.

Rules:

- Final text must answer the buyer's current message.
- Every factual claim has support or is marked as uncertain/inference.
- Commercial limits must be phrased as safe process, not final promises.

### `PreSendReviewer`

Input:

- answer contract;
- ledger snapshot;
- latest user message;
- tool artifacts;
- business rules.

Output:

- `PreSendReview`.

Rules:

- Block only evidence-backed issues.
- Do not block style or harmless wording.
- If no concrete `factId/questionId/claim` supports the issue, downgrade to `nonBlockingNote`.

## Recovery Policy

If `user_message_saved=true`, the buyer must not be asked to repeat the question.

Recovery steps:

1. Load `turn_checkpoints`.
2. Load ledger snapshot and tool artifacts.
3. If assistant message already saved, return it.
4. If ledger delta not applied, rerun state extraction or apply saved valid delta.
5. If tool requests exist but artifacts missing, rerun tools idempotently.
6. If answer contract missing, rerun `AnswerWriter`.
7. If review missing and risk requires review, rerun `PreSendReviewer`.
8. Save one final assistant message under the same `turnId`.

Retry limits:

- LLM contract repair: 2 attempts.
- recoverable tool call: 2 immediate attempts, then queued retry if tool is not required for current answer.
- lead outbox delivery: exponential retry, not buyer-facing.

Idempotency:

- unique `(sessionId, turnId, checkpoint)`;
- unique `(sessionId, turnId, toolRequestId)`;
- unique final assistant message per `turnId`;
- unique lead outbox per `(leadId, destination)`.

Rollout:

1. Enable shadow trace.
2. Run evals.
3. Enable one capability.

5. Remove/disable legacy path for that capability.
6. Continue next capability.

Rollback:

- disable capability flag;
- keep ledger events read-only;
- do not re-enable legacy direct state writes;
- preserve checkpoint and trace data for debugging.

Rollback triggers:

- generic errors appear in saved-turn cases;
- lead duplication;
- repeated known-question regression;
- PII appears in redacted trace;
- p95 latency exceeds agreed tier budget for two consecutive live checks.
