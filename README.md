# БАКАУТ AI Sales Assistant

Продовый AI-менеджер для сайта БАКАУТ. Он ведёт свободный диалог с покупателем, консультирует по строительному и силовому оборудованию, уточняет задачу, проверяет факты, подбирает товары, показывает согласованные с ответом карточки и передаёт заявку профильному специалисту.

Активный production runtime один: `AgentManagerOrchestrator` + GPT-5.6 Luna (`gpt-5.6-luna`) через OpenAI Responses API. LLM отвечает за понимание смысла и стратегию разговора; код — за каталог, схемы, доказательства, жёсткие ограничения, безопасность, побочные эффекты и восстановление.

## Локальный запуск

```bash
cp .env.example .env
docker compose up -d
npm install
npm run migrate
npm run dev
```

Локальный виджет доступен на `http://localhost:3010/widget`. Он подходит для UI-разработки и проверок с моками. Локальные вызовы OpenAI в этой среде не являются валидной проверкой поведения; release-проверка AI проводится только после GitHub/Railway-деплоя через встроенный виджет на `https://bakautprof.ru/`.

## Конфигурация

См. `.env.example`. Для production обязательны `DATABASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL=gpt-5.6-luna`, `ADMIN_API_KEY`, `PUBLIC_BASE_URL` и HTTP email-настройки. SMTP не используется. Семантическое решение, оценка результатов поиска, генерация и проверка ответа работают на `gpt-5.6-luna`. Перед сохранением ответа LLM проверяет его согласованность с полученными фактами и язык общения, а код проверяет контракт и привязку доказательств. При исправимой ошибке тот же writer получает замечания; отдельного fallback-ответа нет. `CATALOG_STALE_AFTER_HOURS` по умолчанию равен `48`.

## Надёжность диалога

- Виджет генерирует стабильный `clientMessageId`; повтор того же HTTP-запроса восстанавливает тот же turn, а два одинаковых сообщения пользователя остаются двумя отдельными turn.
- Один session не исполняет два turn одновременно; lease, checkpoints и tool artifacts позволяют продолжить прерванный turn без повторных инструментов и заявок. Остановка продолжения по бюджету сохраняется; восстановление использует принятый исправленный ответ.
- Финальный response payload сохраняется до доставки клиенту и восстанавливается вместе с текстом, карточками и metadata.
- Уточнение до поиска является самостоятельным шагом: оно обязано содержать вопрос покупателю и не требует преждевременной карточки. Проверка языка охватывает ответ и видимую причину рекомендации в карточках; отсутствующий или некорректный результат проверки блокирует отправку.
- Web research сохраняет привязку факта к точной модели или подтверждённой области общей инструкции. Ошибки чтения источника отделены от отклонения доказательства; bounded `sourceDiagnostics` в защищённых tool artifacts содержит только безопасные URL, код, HTTP-статус и длительность. Уже выполненные чтения восстанавливаются вместе с каталоговыми моделями без повторного расходования бюджета поиска.
- Поиск руководства сохраняет найденные `sourceCandidates` отдельно от проверенных фактов. Реально найденный PDF может быть прочитан для извлечения недостающих сведений; новые утверждения проходят прежние проверки цитаты, модели и издателя. Таймаут чтения не означает, что сведений в руководстве нет.
- После первого поиска LLM оценивает фактические результаты и выбирает ответ, уточнение покупателю или следующий поиск. Доступны до двух дополнительных раундов чтения каталога и web; повтор одинакового запроса, неизвестные товарные ID и побочные действия в этом цикле запрещены. Все стадии делят лимит 150 секунд, 8 модельных стадий, 8 инструментов и 2 web-вызовов; причина остановки сохраняется отдельно от результата поиска.
- Память хранится как semantic dialogue ledger: одна активная потребность, приостановленные задачи, факты с областью действия, моделью, единицей и отношением к требованию. При смене задачи её ограничения остаются в собственной области, а общие ограничения диалога сохраняются. Snapshot + новый tail сохраняют актуальное состояние длинного диалога; старый несовместимый snapshot восстанавливается из исходных событий.
- История карточек сохраняет порядок и идентификатор каждого показа для ссылок вроде «первая из прошлого списка». Совпадение модели учитывает суффиксы; отсутствие характеристики сохраняет товар как предварительного кандидата, а доказанное противоречие исключает его. Явно требуемая независимая web-проверка не подменяется данными каталога или памятью.
- Подтверждённые факты точной модели передаются планировщику, автору и проверке ответа даже без нового web-запроса. Учитываются срок действия, статус, модель и источник; конфликтующие значения передаются отдельно и не разрешают утверждать одно из них как подтверждённое. При восстановлении черновика доказательства проверяются заново.
- Повторное исследование получает изменённую цель планировщика и ограниченный контекст предыдущих попыток по тем же моделям. Таймаут документа помогает выбрать следующий источник, но не означает отсутствие характеристики. Неудачное извлечение фактов из каталога не удаляет исходные характеристики и ссылки товара из контекста поиска.
- Пакетная проверка источников хранит каждый уникальный фрагмент документа один раз; отдельные утверждения ссылаются на него. Цитаты, точная модель и область применимости проверяются для каждого утверждения.
- Предпочтения выбора сохраняют смысл, область действия и `payload.ranking: { attribute, direction } | null`; исходное значение факта остаётся отдельно. При следующем подборе проверяется согласованность памяти, требований и исполняемой сортировки; техническая консультация по выбранной модели не требует нового ранжирования.
- Продолжение вопроса о модели без повторения названия использует проверяемую ссылку `ProductMention.sourceMessageId` на прежнюю точную цель или карточку. Planner получает такие цели и после технических ответов без карточек; название внутри свободного поискового запроса не заменяет структурированную привязку товара.
- Решение продолжения «нужно уточнить» проверяется перед отправкой: финальная пригодность не объявляется до уточнения, а предварительные варианты могут сопровождать вопрос. В ledger регистрируются вопросы принятого ответа, включая исправленный writer-ответ; вопросы отклонённого черновика не попадают в память.

## Admin и наблюдаемость

Admin endpoints требуют `Authorization: Bearer <ADMIN_API_KEY>`.

- `/api/admin/conversations`, `/:id`, `/:id/agent-traces`
- `/api/admin/leads`, `/api/admin/conflicts`, `/api/admin/products`
- `/api/admin/feedback` и `/api/admin/feedback/:id/export-candidate`
- `/api/admin/catalog/freshness`, `/api/admin/embedding-coverage`
- `/api/admin/health` — модели, полный runtime manifest, catalog/embedding/outbox health
- `/api/admin/runtime/openai`, `/api/admin/openai-usage`

Публичный `GET /api/health` содержит только deployment marker: commit и минимальные runtime/contract версии. Модели, полный список runtime artifacts, policy hash и операционные сигналы доступны только в защищённом `/api/admin/health`.

## Деплой и проверка

Изменения уходят только через `git commit` + `git push`; Railway автоматически собирает GitHub-ветку. Ручной `railway up/deploy` не используется. После появления нового commit marker в `/api/health` проводится адаптивный диалог через виджет на `bakautprof.ru`, затем каждый turn сверяется с карточками, trace/metadata и кодом. См. `docs/RAILWAY_DEPLOY.md` и `docs/LOCAL_LIVE_TESTING.md`.
